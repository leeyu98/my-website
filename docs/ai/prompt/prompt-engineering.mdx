提示词工程（`Prompt Engineering`）是通过设计高质量的输入来引导 LLM 产出期望输出的技术。以下是一些经过验证的实用技巧。

## 基本原则

### 1. 明确的角色设定

```text
# ❌ 模糊
帮我写点代码。

# ✅ 清晰
你是一名有 10 年经验的 Python 后端工程师。
请用 FastAPI 写一个用户登录接口，包含 JWT 认证。
```

### 2. 结构化输出指令

直接告诉模型你想要的输出格式：

```text
请将以下内容总结为 3 个要点，每条不超过 30 字，以 markdown 列表形式输出。
```

如果需要 JSON 输出，直接描述 schema：

```text
请以 JSON 格式输出，结构为：
{
  "name": "string, 人名",
  "age": "number, 年龄",
  "skills": "string[], 技能列表",
  "summary": "string, 50字以内的总结"
}
```

### 3. Few-shot（少样本示例）

在 prompt 中提供一两个示例，模型能更准确地理解你的预期：

```text
将下面的英文日期转换为中文格式：

输入: 2026-01-15
输出: 2026年1月15日

输入: 2024-12-31
输出: 2024年12月31日

输入: 2025-07-01
```

## 进阶技巧

### Chain of Thought（思维链）

让模型**逐步推理**而非直接给出答案，显著提升复杂任务的准确率：

```text
# ❌ 直接要求答案
这串数字的规律是什么？2, 5, 10, 17, 26, 37

# ✅ 要求逐步推理
这串数字的规律是什么？2, 5, 10, 17, 26, 37。
请先列出相邻两项的差值，再推导出第 10 项是多少。
```

### 分步拆解复杂任务

不要用一条 prompt 完成所有事情。将复杂任务拆分为多个步骤：

```text
步骤1 → 分析需求，列出关键要点
步骤2 → 根据要点生成大纲
步骤3 → 根据大纲逐段展开
```

### 反向约束（Negative Prompting）

明确告诉模型**不要做什么**，效果往往比只说要做什么更好：

```text
# ❌ 只说要求
请用友好的语气写一封邮件。

# ✅ 加上约束
请用友好的语气写一封邮件。
- 不要使用感叹号
- 不要出现"亲爱的"
- 字数控制在 100 字以内
```

### 引用原文（Verbatim Reference）

要求模型引用原文的关键部分再作答，减少幻觉：

```text
根据以下文档回答问题。回答时先引用相关原文，再给出你的分析。

文档内容：
...

问题：...
```

## 常见陷阱

| 问题 | 表现 | 解决 |
| --- | --- | --- |
| 提示词过长 | 模型忽略中间部分的指令 | 把最重要指令放开头或结尾 |
| 指令冲突 | 同时要求简洁和详细 | 分两次请求或设定优先级 |
| 过度引导 | 限制了模型的推理空间 | 减少"必须"、"只能"等词 |
| 上下文污染 | 多轮对话后模型带偏 | 必要时重置对话或总结关键点 |
